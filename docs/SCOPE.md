# Current implementation scope and decisions

Updated 20 October 2026. This records accepted product decisions; implementation status is tracked separately in the requirements catalog.

## Package namespace and pack growth

Use `@notabenda/core`, `@notabenda/cloudflare` and `@notabenda/authoring`. The free npm organization is reserved; package publication remains a separate future action. Keep the CLI in core and preserve the installed `notabenda` and `notabenda-cf` binary names. Packs remain selectable modules rather than separate packages. Preserve retained data/provenance identifiers, hashes, browser keys and saved selections across the naming change. See [package naming](PACKAGES.md).

The twenty installed packs do not exhaust the compliance overview. Form notices, Indirect collection, Privacy requests and Processing opt-outs now have focused setup paths; the five consumer jobs now have separate setup paths. Technology notices, assessed storage settings and Google Basic now have focused setup paths too. The [pack roadmap](PACK-ROADMAP.md) records available setup paths and the admission rule. Admission requires connected questions, configuration, examples, requirement references, host tasks and failure checks; do not inflate availability with labels alone.

The website footer groups exploration, building and project references, with separate privacy/license links and a restrained Inferal sponsorship credit. Keep it usable on small screens, with native links and visible keyboard focus.

## Build the basics first

- Ship a reusable npm package with typed site configuration, validation, and privacy/cookie/terms documents that can be rendered as ordinary HTML or inside a host application's layout.
- Support supplied terms and policy text. Generated disclosures must derive from explicit operator facts. Draft/review declarations are visible and production output must not silently accept unresolved placeholders.
- Keep browser/SSR imports dependency-free and separate from Node build tools. The optional Cloudflare component is a separate package, `@notabenda/cloudflare`.
- React 19 integration is an optional `@notabenda/core/react` subpath, with an optional React peer; default imports remain framework-independent. The host supplies one controller, registers services outside React render/effect remounts and owns its destruction. Hooks expose effective permissions separately from saved choices, with conservative SSR/hydration. Server-safe legal wrappers use `@notabenda/core/react/documents`.
- Astro integration uses optional packaged `.astro` surfaces and a `@notabenda/core/astro/client` lifecycle bridge around the same host-owned controller. Static legal pages need no scripts. Interactive pages reuse the controller through client navigation, close unsaved drafts on swaps and remount controls once. Keep a working preferences surface on every client-routed page where optional services continue. The actual Astro 7 example build requires Node 22.22+; broader framework/platform review remains separate.
- The project website is a documentation and distribution home: installation, API/integration guides, requirements and primary sources, feature status, and interactive examples. Examples support the documentation; they do not define the site's entire purpose.
- Authoring accepts JSON through the CLI and structured JavaScript/TypeScript objects through the build API. The optional `@notabenda/authoring` build package supports both Markdown (`.md`) and MDX (`.mdx`) with YAML frontmatter for title, route, version, effective date, review status and stable section IDs. MDX supports host-supplied static components as trusted build-time project code; the core stays framework-independent. Original source is archived privately alongside rendered output, with separately authorized source inspection and comparison. Shared operator/processing inventory stays reusable in site configuration. See [the authoring guide](AUTHORING.md) for format, trust boundaries and preview size limits. Word/PDF conversion remains later, reviewable import work.
- Keep work uncommitted and unpublished until instructed otherwise. Project content and examples must not record private business details or the origin story.

## Cloudflare backoffice

- Provide pluggable workers and storage adapters, including a fixed-scope Durable Object adapter, for an operator to mount a backoffice in its own application.
- **Authentication and authorization belong to the host application.** The package supplies no account system, login UI, credential store, or identity provider. Require a caller authorization hook and fail closed when access is absent or fails.
- The host binds the authorized store/site scope. Do not expose a browser route for arbitrary Durable Object IDs or namespaces.
- Present information around compliance questions: what happened, when, to which subject/site/purpose, against which notice/version, with which provenance and retention information when recorded. Never invent missing evidence.
- Prefer searchable evidence cards, chronological summaries, readable detail views, and targeted comparisons. Tables and raw JSON are supporting views, not the entire interface. Bound search work and explain partial/continued results.
- Maintain one responsive admin frame across records, comparisons, lifecycle, export, demo overview and guided setup. Host-supplied navigation is presentation only; every destination retains its own authorization. Setup uses six navigable stages and grouped practice cards with direct choices, with local-only notes and explicit review/export.
- Durable Objects are an explicitly supported storage path for this component. Earlier D1 designs are alternatives for later evidence services, not a mandatory dependency of this admin package.
- `notabenda-cf init` generates a new local standalone Worker project with SQLite class exports, fixed configured-site selection, the shared admin/setup UI and an initially denying host authorization hook. It preserves existing paths and performs no network, install, login, provisioning or deployment. Generated Wrangler scripts make local build/check/dev and remote deployment explicit. Private archive RPC checks site identity; public recording/identity/activation policy, operations and any deployment doctor remain separate work. See [the starter guide](CLOUDFLARE-STARTER.md).

## Terms and policy change history

- Provide mechanics to retain immutable released versions of privacy, cookie, and terms documents, including exact content, identifiers/digests, version/effective-date metadata, and an explicit change note when supplied.
- Make history inspectable in the backoffice, with previous/current version comparisons and readable diffs. Cosmetic/rendering changes must be distinguishable from authored content changes; a diff does not itself decide legal materiality.
- Archive the privacy, cookie, and terms documents together as a reproducible release. Preserve structured content and rendered HTML, verify their digests, and reject attempts to replace an existing release with conflicting content or change metadata.
- Show document versions, effective dates, recorded dates, optional actor/change notes, and content differences in human-readable views. Treat recorded dates and publication/effective dates as separate facts; never infer that storage means a document was published.
- Recording or reviewing a release does not publish it, notify users, obtain consent, or accept terms. Those are separate host/application actions.
- Retain earlier versions needed by evidence records, with operator-controlled retention/erasure and no claim that an append-only application log is undeletable.

## Explicit terms agreement

- Keep an unchecked terms statement separate from privacy notices, cookie choices, and optional marketing permissions. Bind the exact terms HTML/content and interface wording into an immutable offer.
- Register an archived offer separately from explicit host activation. The trusted host binds site, subject, intended workflow and operation; browser fields cannot supply that authority.
- Report recorded agreement only after a matching persisted receipt. Check the active offer and write new agreements in one transaction; uncertain retries recover the original record without changing its version.
- Show agreement context in the authorized backoffice. A stored assertion is not proof of identity, a human click, legal enforceability, delivery, or completion of a related purchase/signup.
- The host retains and serves pinned versions, implements authentication/CSRF/operation authorization, and owns retention, replay policy, delivery and business actions. Paid checkout and applicable consumer actions require their own reviewed flows.

## Durable cookie-choice reports

- Keep the local-only controller independent. Optional server helpers register an immutable notice, activate it explicitly, and bind exact wording, purpose scope and archived privacy/cookie versions to each report.
- Host authorization resolves the site, intended scope and opaque stream. The package supplies no login, public account binding, raw capability storage or identity recovery.
- Append events and advance the stream head atomically. Grant-bearing snapshots require a matching current revision and active notice; stale grants need a new deliberate choice. An explicit revoke-all may arrive from a known older notice and clears newer purposes too.
- Idempotent retries return the original historical receipt together with the current head; they never replay the historical command. Keep client-reported time separate from server receipt time and do not extend expiry through retries.
- Present historical purpose cards, exact notice wording, causal revisions and document references in the backoffice. Choice expiry is distinct from evidence retention. Host retention, erasure, audit and replay policy remain required production work.
- Browser delivery and required-receipt gating are opt-in at controller construction before optional work can start. Saved local choices remain separate from effective permission. Bounded retries preserve the original action, head reads confirm current evidence after reload/resume, and late acknowledgments cannot replace refusal. Public local-only and session-isolated recorded-choice examples remain distinct.

## Pack product model

Notabenda should feel like inserting a pack for a clear job. Lead with a small library, a deliberate selection and gradual setup that teaches the decisions as they become relevant. The visual direction is console-like simplicity: a few recognizable packs, a visible setup tray and an obvious next action. Keep the established restrained design; do not imitate another product's branding or turn regulatory coverage into game achievements.

Start with privacy pages, cookie choices and terms agreement. Show additional functions and named regional rules in visible groups alongside the basics. A regulatory pack adds specific supported policy proposals, questions and checks; it does not assert complete jurisdiction coverage. Framework/package/backend choices come at connection time.

Use one versioned pack registry referencing the existing integration and requirement contracts. Selection defines planned work. Supporting foundations are inspected and reused, rather than silently enabled. Ask relevant practice questions without marking unseen jobs or unknown facts as no. Keep complete diagnostics and supporting information accessible.

Export and resume must preserve selections, explicit answers, the current draft and private justifications. No sensitive browser persistence is added by default. Removing a pack removes planned work; it must not silently delete existing config. A selected pack is not an installed integration, and a valid draft is not a verified deployment. Future verification states need evidence bound to the actual configuration, release and integration revision.

The pack selector and local editing-session controller are reusable package exports with a separate stylesheet. Hosts supply optional example, map and guide destinations. The website and new CF starter use this component for setup; host authorization still protects starter assets before they are served. Existing hosts may keep the direct questionnaire entry. Remaining evidence dashboards and evidence-bound verification states are separate work.

The evidence overview groups three primary record jobs and folds additional areas. A shared, host-authorized record finder searches one bounded segment per allowed store, with distinct continuation, empty and unavailable states. Normal overview requests read no records; source/file inspection and exports retain separate grants. No count, sample or stored event establishes current permission, installation or legal readiness.

Pack draft review includes an optional local page reader. It renders a fixed public projection with the existing legal renderer, preserves document review declarations and disables outside navigation. It never imports private reports into the viewer, executes MDX, publishes a release or activates a tool. Separate project MD/MDX/custom-component builds and deployed behavior still require their own previews and verification. The reader loads on request in the website and generated starter and retains host configuration access controls.

The product calls these jobs **packs** and keeps the existing physical pack artwork. All twenty installed packs are visible in five groups, with an index showing the group counts. Additional functions and regional mechanisms are not hidden in a foldout. The three basics are a starting point, not the full library. Existing command/import aliases and saved selections remain compatible (REQ-PRODUCT-CARTRIDGES).

Pack discovery must work before entering setup. The homepage and architecture guide show the complete installed library in groups, with each name linked to its setup card. The main navigation carries the pack count, and the setup index names all twenty. Shared registry data supplies the website overview and its text version; no separate marketing list determines availability.

Cookie control settings can be authored through setup and the interactive CLI, using the same draft API. Require explicit service selection, the full set of linked purposes, material-version labels and separate grant/refusal/dismissal memory. Bind saves to the reviewed public config, invalidate old exports on adoption and preserve existing restrictions, timing policies, rights links and catalog reviews. Do not supply legal defaults, relax unknown scope declarations, register vendor code or claim the deployment works from settings alone (`REQ-PRODUCT-CONSENT-AUTHORING`).

Scoped draft preparation includes a pack-specific connection guide and a matching saved agent brief (REQ-PRODUCT-PACK-CONNECTION). It reuses installed target tasks, checks and guide links, distinguishes foundations, and preserves exact disabled regional proposals. The scoped CLI saves the brief beside the config and private report with owner-only permissions. Neither the guide nor a generated brief records installation, completion or verified deployment.

The four added privacy packs retain separate direct/indirect targets and language limits, rights-entry prerequisites and independent processing-signal/recording decisions. Questionnaire revision 6 accepts prior reports with new answers unresolved. Regenerated private input reviews identify missing declarations and manual builder/host work in the UI, report and matching agent brief; they never mark configuration or deployment complete. See [privacy packs](PRIVACY-PACKS.md) (`REQ-PRODUCT-PRIVACY-PACKS`).

Publication checking is an explicit local operator action: four anonymous reads of pinned files against a trusted artifact, with bounded bytes/deadlines and no redirects. It provides no installed-pack status, current-route/active-control verification, atomic snapshot or legal approval. See [publication checking](PUBLICATION-CHECK.md).

Consumer packs keep withdrawal, supported German cancellation, paid orders, customer copies and guarantee displays independently selectable. The confirmation path explicitly needs its existing received Cloudflare order admission and retained review. Separate builder inputs remain host work rather than fictional SiteConfig fields. Markets/locales never select profiles or establish guarantee qualification. Old setup reports retain answers and leave new facts unresolved. See [consumer packs](CONSUMER-PACKS.md) (REQ-PRODUCT-CONSUMER-PACKS).

Three specialist packs add explicit setup for technology notices, assessed storage objections and Google Basic. Their prerequisites remain distinct: technology/Google reuse consent; exception-managed work stays outside it. Setup preserves unknowns, existing profiles and mappings, and treats builder/host work as unresolved. Google target assessment requires one populated declaration among service items, without requiring that property on unrelated services or inferring shared-page ownership. Questionnaire revision 8 reads revisions 1–7 and leaves added facts unknown. See [specialist packs](SPECIALIST-PACKS.md) (`REQ-PRODUCT-SPECIALIST-PACKS`).
