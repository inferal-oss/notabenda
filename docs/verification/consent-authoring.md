# Consent settings authoring verification

Requirement: `REQ-PRODUCT-CONSENT-AUTHORING`.

The shared draft API accepts only bounded plain data and five explicit core settings fields. It compares the reviewed public baseline with current public configuration, requires complete selected-service purpose coverage, and uses the existing configuration/exception validator. Tests exercise missing/invalid versions and lifetimes, duplicate/unknown IDs, incompatible exception ownership, omitted optional-storage services, accessors, stale public facts and detached results.

UI tests cover fresh empty fields, visible multiple-purpose effects, cancellation, rejected stale saves, sanitized host failures, in-place setup navigation, invalidation on save, preserved catalog pins and private-note separation. CLI tests use the same draft plan, preserve imported values or unresolved blanks, require confirmation, and resume actual scoped wizard output. Neither interface infers a legal basis or regional policy, supplies legal defaults or relaxes scope guards.

Regression checks keep Enter in both material-version and numeric fields inside the current setup stage. CLI confirmation rechecks the public baseline after the operator's final answer. Installed-tarball tests import both new subpaths without browser globals and compile strict consumer types. An optional status-notification failure cannot undo an already adopted draft or expose its exception text.

Actual synthetic service lifecycles exercise the authored output in both compatibility and compiled consent engines. Initial load and rejection start nothing; granular grants affect only permitted services; withdrawal runs cleanup; reload retains choices. Explicit unknown/present scope guards prevent starts. These tests use fictional local services and memory adapters. They do not verify an adopter's actual loaders, network traffic, deployment or legal applicability.

Semantic accessibility checks and separate native-browser layout/keyboard checks cover the editor. JSDOM alone does not certify layout, screen readers or physical devices.

Chromium verification used an explicitly fictional local inventory with two services and two purposes, with no consent settings. Fresh fields were blank. Selecting the two-purpose service exposed both purpose-version fields; an incomplete save focused the first missing version. Enter in a version field and numeric field stayed on Site. At a 390px viewport, document/client widths were both 375 CSS px, fields used 16px text and the grids stacked into one column.

The prepared browser download contained exactly the entered service/purpose versions and three memory values, retained the unresolved scope guards and kept document reviews as draft. Loading that downloaded config into the actual controller still denied the selected service after an attempted grant. These are synthetic workflow checks, not tests of an adopter's provider integrations or legal review.
