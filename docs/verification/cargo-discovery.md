# Cargo discovery verification

The static scanner and CLI exercise normal, optional, development, build, workspace and target-specific declarations; package renaming; six exact source-linked crate names; TOML comments, prose, dotted/quoted keys and metadata confusers; unresolved inheritance; source redirects and overrides; malformed shapes; duplicate keys; nesting, entry and file-size limits. Selected Cargo configuration paths flag limited coverage without reading values. Tests retain Git ignores, credential exclusions, symlink boundaries, private export permissions and exclusive output creation. Cargo/rustc shims and build scripts are never invoked.

An offline packed consumer runs the installed wizard against a Cargo manifest and retains an unselected candidate. Runtime and public-schema checks share name/prefix bounds, and catalog updates preserve historical selection pins. The existing Python cases exercise the same bounded TOML reader. Its pinned parser remains bundled only in Node discovery with the original BSD-3-Clause license; ordinary visitor controls do not import it.

This is declaration discovery, not Cargo validation, registry ownership, dependency resolution, installation or production-use verification. Workspace definitions need not be consumed; inherited aliases are not guessed. Features, targets, lockfiles, Rust imports, ancestor/global configuration and environment overrides remain unresolved. Private paths/conditions/aliases, registry values, versions, metadata and source text stay outside findings. A named client may use local or self-hosted infrastructure. Actual endpoints, provider relationships and processing facts require review; the broader requirement stays partial.
