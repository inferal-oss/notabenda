# Terms retry recovery checks

Checked 22 October 2026. The optional helper preserves a private request key across page reload; it restores neither acceptance nor a receipt. The ordinary controller and host-authorized recorder retain their existing contracts.

## Automated evidence

The package suite passes 1,353 tests. New coverage includes reopening IndexedDB after a committed but lost receipt, eight simultaneous journal instances reserving the same key, changed operation/offer/wording/localized copy, corrupt and accessor-bearing records, unavailable/replaced/missing storage, destruction during a pending read, option mutation during initialization, transaction rollback, row bounds and explicit per-context cleanup. The packed-package consumer checks runtime imports without browser globals and strict TypeScript usage.

The actual loopback HTTP fixture interrupts its first receipt after server commit. A new controller and reopened journal then remain unchecked and send nothing until a new explicit action. Retry returns the original receipt, with two attempts and one record. Separate tests keep the original same-controller retry, bounded fault injection, request guards and pinned reader checks.

The independently measured recovery entry is 4,155 bytes gzip under esbuild 0.28.2, ES2022, minification and gzip level 9. Its graph excludes backend, build, setup and framework modules. The compiled-local, required-evidence and compatibility consent reports and consent-only CSS remain exactly unchanged. The compatibility 15 KiB target remains open.

## Browser evidence

The actual local HTTP rehearsal was exercised in in-app Chromium. Initially unchecked, checking alone left the server at zero attempts. The first explicit submit produced an unconfirmed UI while the server showed one stored record. Reload displayed an unchecked, unconfirmed control and left the server at one attempt. Checking and submitting again produced a confirmed UI; independent server observations showed two attempts, one record, the same command and the original receipt.

The vanilla example was also checked through a separate local Worker and session-isolated Durable Object. It loaded the recovery module, saved the sample assertion, reloaded unchecked and confirmed again only after an explicit check/retry. The independent one-record observations above come from the controlled HTTP fixture.

This checks a real page reload and interrupted HTTP response against the actual example transport. It does not establish physical-device, screen-reader, Safari, Durable Object restart or operational acceptance coverage.

## Limits

Atomic journal reservation is not authenticated subject binding. A retained key is not evidence of a checked box. The pre-submit read is a point-in-time check; it cannot fence later storage changes in another tab. Clearing or evicting the complete row before initialization can create a new key, so server operation deduplication remains separate. No automatic expiry or eviction is supplied. The host coordinates cleanup with all controllers and settles or retires operations on the server. No real contract or personal data is used by the rehearsal.
